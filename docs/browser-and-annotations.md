# Browser shell and user annotations — design only

The primary product is a downloadable, self-contained HTML memory aid for close friends and family. The tool supplies evidence; the user supplies meaning. An annotation such as a holiday or starting university belongs to the user, not to an inferred life narrative. No installer, hosted upload service, account, runtime CDN, telemetry or AI is required. CLI and MCP remain other shells over the same engine; MCP is built last. None of this browser work is implemented yet. Step 6 is accepted. Step 8 report design now precedes step 7 diffing; the presentation specification is [step-8-report-design.md](step-8-report-design.md), pending review.

## One engine, separate capabilities

The existing `ParserInput.readJson(relativePath)` and optional `iterateJsonRecords` boundaries can accept a browser reader returning the same result types. Browser File APIs expose user-selected files, not arbitrary filesystem access. This confirms the direction of the interface, not browser compatibility of the whole current package. See the [File API documentation](https://developer.mozilla.org/en-US/docs/Web/API/File_API).

Current blockers found in code:

- `instagram-encoding.ts` uses `Buffer.from(value, 'latin1')`. Replace this with byte-array construction plus the existing strict `TextDecoder`, preserving representability checks and regression results; do not silently switch to forgiving decoding.
- `input.ts`, `ingest.ts`, `snapshots.ts`, `side-table-store.ts` and command modules depend on Node filesystem/crypto/path APIs. Keep their persistence and atomic-publication implementation in the Node shell; the browser must not import that dependency graph.
- `ParseResult.events`, side tables and the current exploration results are materialised. A different reader does not remove those allocations. Existing per-artifact 32 MiB limits are Node implementation limits, not a browser capacity benchmark.
- Browser cryptographic hashing, worker scheduling, cancellation and persistence need injected shell capabilities. No eager Node import or implicit filesystem path may appear in the portable engine/report model. Build-time TypeScript bundling is separate from runtime dependencies and requires its own justified build choice.

Proposed capability shapes, not implemented interfaces:

| Capability | Contract |
| --- | --- |
| Selected source | Immutable handles to user-selected Files/Blobs or validated ZIP entries; logical relative paths and sizes only |
| Reader | Existing readJson/iterative results, bounds, strict decoding and read audit; no writes or network |
| Engine | Normalised observations, side tables, descriptive evidence and selected method results; no DOM or filesystem |
| Report model | Structured data handed to a renderer in memory; no output directory, automatic write or assumed filename |
| Persistence | Explicit user export/import of a versioned local bundle through Blob downloads/file selection; Node shell can use its current disk store |
| Execution | Progress and cancellation; browser worker can own source handles and analysis so large arrays need not be copied between threads |
| Disclosure | Declared-path policy plus actual read outcomes, generated by the same reader boundary that grants access |

A self-contained application file is not automatically a self-contained personal report. Opening the downloaded application starts empty. The user can choose to save a personal bundle or a new HTML copy containing their data and annotations; those exports must warn about their contents. The browser cannot assume it can overwrite the original HTML, find Documents/Hindsight, or persist reliably under a `file:` origin. Default to memory during a session and explicit save/import; browser storage, if offered later, is optional and must explain eviction and clearing. Unsaved annotation changes need a visible reminder. No service worker or loopback server is required for the primary shape.

## Memory and workers: corrections to the planning assumptions

The roughly 30 MB Instagram input is a reasonable first browser target, not proof that it needs no special handling. Earlier parser Node measurements were roughly 188–218 MiB RSS; the complete step-6 analysis/output batch peaked at 464.63 MiB. Both have different runtime and object overhead from a browser. ZIP inflation, decoding, repair, JSON parsing, side-table joins and rendering can coexist in memory. Avoid whole-archive inflation and duplicate full buffers; parse declared files sequentially, release intermediates, and measure Windows/macOS target browsers before promising compatibility.

Use a worker for ZIP/JSON/statistical work already at step 8 where supported; it keeps the page responsive and enables cancellation. It does not make memory bounded. Test inline/Blob worker bootstrapping from the downloaded `file:` HTML with the final CSP in Chrome/Edge, Firefox and Safari. A missing capability must produce an honest limitation, not a frozen tab or network fallback.

The 100–300 MB YouTube case still needs step 9's complete incremental pipeline: `File.stream()`/Blob streams, incremental JSON-array parsing, incremental coordinator, joins/aggregation with bounded state and an output/storage strategy. Takeout watch-history JSON must not be assumed to be NDJSON. NDJSON can be an internal/export format; converting an entire input to NDJSON in memory first solves nothing. See [streaming-contract.md](streaming-contract.md). Instagram ZIP decompression can stream earlier without claiming the whole engine is streaming.

## ZIP cost and dependency decision

Browser decompression primitives do not provide a complete ZIP reader with entry selection and archive validation. They decode compression streams; archive metadata and path/security logic are separate. See [DecompressionStream](https://developer.mozilla.org/en-US/docs/Web/API/DecompressionStream).

One audited ZIP dependency is justified for step 8 instead of writing and maintaining an archive decoder. **zip.js is the evaluation candidate, not an installed or approved pinned version.** Its documented entry/stream and worker facilities fit selective opening, but application resource limits remain our responsibility. Select a reader build that can be bundled entirely into the HTML, with no worker/script/WASM fetch at runtime. Measure the pinned build's actual bytes and license obligations before adoption; no download-size or speed number has been measured for HINDSIGHT. [zip.js documentation](https://gildas-lormeau.github.io/zip.js/).

The cost is added bundled code and license/update review, archive metadata parsing, CPU for inflating only selected entries, memory for bounded compressed/decompressed buffers, and adversarial/browser testing. It is not the cost of expanding the entire archive. No chart or burst-detection dependency is justified by this decision.

ZIP rules must include: bounded archive metadata/entry counts and filename lengths; exact logical path matching after explicit selection of one export root; reject absolute/traversal paths, duplicate or ambiguous matches, links, overlapping/mismatched headers and unsupported selected-entry encodings; cap selected-entry and total expanded bytes during reading, not only by claimed sizes; check selected-entry integrity; reject nested archive traversal; support cancellation. Unknown payloads are never inflated. Enumerating archive filenames/sizes reads metadata, and must be disclosed separately from opening entry contents. A large unrelated media entry need not be decompressed merely to ignore it. Test untrimmed exports at step 8 through this boundary; cancellation of quarantine does not cancel those tests.

## Offline behaviour and disclosure

Opening a local HTML file may feel like a website asking for a private upload. Say what actually happens: select a local file; its permitted contents are processed in this tab; nothing is sent. Make the offline check a first-class acceptance test and user explanation: **“Turn off your wifi. Now use it. It still works.”** The download must contain its scripts, styles, worker and codecs. No remote images, fonts, thumbnails, frames, analytics, automatic links or deferred sync. A file-open demo proves functionality offline, not immunity to a malicious browser extension or tampered copy. Browser download warnings may still exist; cancelling the .exe does not promise warning-free downloads.

Use a restrictive bundled CSP, safe text rendering and a request-denial test harness. Metadata paths are untrusted. Opening external source links is never required for the memory aid and must be an explicit action that explains leaving the local page. See [threat-model.md](threat-model.md) for evidence-backed disclosure and MCP's different trust boundary.

User guidance: **“Your export contains sensitive material; you may want to delete the ZIP yourself after use.”** HINDSIGHT never deletes originals or working copies as a privacy operation. Keeping an export for future snapshot history remains the user's choice.

## Annotation data shape

Annotations are a core, optional feature. They are authored, edited, exported and deleted by the user, stored separately from immutable source snapshots. No required dates, account, upload or guessed meaning. Proposed JSON shape (schema only, no annotation file is created now):

```json
{
  "format": "hindsight.annotations",
  "schemaVersion": 1,
  "revision": 1,
  "sensitivity": "personal",
  "events": [
    {
      "id": "locally-generated-uuid",
      "kind": "period",
      "label": "User-written title",
      "start": {"earliest": "2025-03-01", "latest": "2025-03-31", "precision": "month"},
      "end": null,
      "timezone": "Australia/Brisbane",
      "notes": "Optional user-written memory; never generated by the tool.",
      "snapshotRefs": [],
      "createdAt": "2026-09-10T00:00:00.000Z",
      "updatedAt": "2026-09-10T00:00:00.000Z",
      "authorship": "user",
      "recordedContext": "after-viewing-evidence"
    }
  ]
}
```

The example dates are invented schema examples, not the user's reference dates. `kind` is `point` or `period`; a point uses `start` only. Endpoint bounds are inclusive local calendar dates with earliest <= latest; exact known dates have equal bounds. Optional uncertainty is represented by unequal bounds. `precision` is day/month/year/approximate and controls display, never tightens the bounds. An unknown end stays null and is visibly open/unknown, not silently extended into a claim about the present. Reject impossible ranges; preserve overlapping uncertain starts/ends as uncertainty rather than inventing an order. Notes and labels are plain text with length limits and safe rendering, including when imported from a local file.

Selecting a range on a rendered timeline fills dates that the user can widen or change. Annotations can span snapshots, which only provide evidence references; annotations are not platform observations or inferred topics. User-authored context must remain visually separate from computed counts. “Factors” means user-supplied contextual markers, not automated causal claims. The user can omit all annotations and still use the tool. User-requested annotation edits/deletion affect only their annotation records, never source export files.

This replaces the blank ground-truth JSON workflow **as the user interface**, not as a guarantee of independent validation. An annotation made after seeing a chart is retrospective contextual evidence, not held-out truth. For any future confirmatory evaluation, explicitly select and freeze a revision/hash and record what data the user had already seen; later edits create a new revision, not a silent overwrite of the evaluation reference. Do not run the superseded ERAS gates against annotations selected after viewing its outputs. No separate reference form is required for ordinary use.

## Step 8 report shape — revised after step 6 acceptance

The authoritative presentation detail and acceptance matrix are in [step-8-report-design.md](step-8-report-design.md). The report opens with exact observed coverage, timezone and the supplied export date, followed by the saved/liked behavioural divergence. Discrete multi-year creator activity leads the historical evidence. Current-folder bursts form a separate nine-month section, explicitly including December 2025 and the unassessed final week in August 2026.

**Burst detection cannot date phases; it can locate recorded concentrations that prompt memories of them.** Eighteen of 46 primary outer intervals retain overlap across all nine settings, including three with identical endpoints. That can be useful for a memory aid without constituting validated life-phase detection. The user supplies dates and meaning. Exact-stable, overlap-stable and primary-only are exclusive agreement tiers: 3, 15 and 28 outer intervals here, not confidence probabilities.

Use a plain SVG swimlane Gantt with one lane per qualifying current folder and overlapping intervals visible. Solid endpoint edges belong only to exact-stable intervals at weekly model resolution. Overlap-stable intervals use measured endpoint envelopes and gradients; primary-only intervals use distinct stipple/fading without a crisp enclosing bar. Compute geometry from the contributing configurations, preserving split/merge and gap structure. Do not invent a certain centre where no week is shared by all configurations. Coverage gaps cut the shapes, including their gradients. The difference survives greyscale, focus, print and export without requiring a caption or hover.

Give all 39 no-primary-bar folders their own descriptive section, titled “Saving patterns without a primary concentration,” with discrete weekly observations, active/eligible weeks, first/last save dates and coverage. Do not infer steadiness from no bar: 17 appear under other settings, two lack assessed weeks, and only 15 have saves in two or more assessed weeks. Repeated saving without a primary concentration is substantive evidence, not failure; the user can recognise a steady interest without the tool assigning that meaning.

Annotations render on the same axes, visibly separate from computed evidence. The annotation's `recordedContext` appears in its inline card/label, details, print and saved/re-imported report, including “Recorded after viewing evidence.” Unknown context stays unknown; prior context is not silently replaced during edits. Edits after viewing are visibly marked with a preserved revision trail. Suggested annotation dates use the uncertainty envelope and remain user-editable; no unstable model endpoints are silently copied as exact memories.

The in-memory versioned timeline model includes coverage, source/display dates, channel activity, discrete lifecycle marks, contributing grid intervals and weekly support, endpoint envelopes, agreement tiers, secondary denominator evidence, no-primary-folder summaries and annotation revisions. It has no filesystem assumption. Source labels remain text, not markup. No chart dependency is proposed. Stable recurrence ordering remains active months, active weeks, then sessions; no percentile, peer comparison, target, moralised vocabulary or generated interpretation. Use “last recorded here.”

Design only: stop for review before browser implementation. The existing portable-engine, selective ZIP, offline, memory, persistence and security acceptance requirements above remain in force; presentation acceptance does not waive them.
